# 実行指示書 — model-domain

`playbook.yml`は工程順・依存・入出力を決める。この文書は、各工程で何を意識するかと、grillへ渡す題材固有の文脈を補う。

## 背景と目的

業務知識・コアドメイン（domain-rule）の正本は、業務として何が正しいかを確定させる。それだけでは、エンジニアが同じモデルを思い浮かべるには足りない。同じ正本を読んでも、何を要素にし、どこに境界を引き、どの操作をどの要素に置くかは人によって違う。

この段取りは、その違いを一つの資料へ収束させる。**成果物は共通理解の材料であって、実装コードではない。** 言語固有の型やクラスの書き方には踏み込まない。

## 前提

- 正本は`discover-domain` / `formulate-domain`が作るdomain-rule型の資料で、`# 概要`から`# BDD`までの見出しを持つ
- 正本の未決は、この段取りで決めない。モデル側の未決として引き継ぐ
- 正本に無い業務の事実が要ると分かったら、この段取りを止めて、正本の反証（formulate-domain）へ戻す

## 工程ごとに意識すること

### settle（grill）で確かめること

**正本と索引から読み取れることは問わない。** 業務用語の意味、業務ルールの成立条件、拒む理由は正本にある。問うのは、正本だけでは一つに決まらない割り当てである。

| 論点 | 問い方 | 推奨の作り方 |
|---|---|---|
| 集約の境界 | 「〈常に守られること#n〉は〈概念A〉の内側だけで守れますか。〈概念B〉も同じ操作で一貫させますか」 | 1つの操作で一貫させたい範囲を最小にする案を推奨し、広げる案は理由を添えて対案にする |
| 状態ごとの型の分割 | 「〈状態を持つもの〉は、状態によって呼べる操作が違いますか。違うなら状態ごとに型を分けますか」 | 正本の「状態と、その移り変わり」で、状態ごとに引き金が違えば分ける案を推奨する |
| 正本に無い語 | 「〈語〉を要素にしたくなりますが、正本のユビキタス言語にありません。正本へ足しますか、要素にせず捨てた割り当てへ残しますか」 | 要素にせず残す案を推奨する。正本へ足すなら、この段取りを止めて反証へ戻す |
| 形が同じ2つの語 | 「〈語A〉と〈語B〉は属性が同じに見えます。目的や場面が違えば別の要素にしますが、同じ概念ですか」 | 別の要素にする案を推奨する |
| 識別子を持つが集約か | 「〈概念〉は〈識別子〉ごとに決まりますが、この文脈で〈概念〉の生成から終端までを扱いますか。それとも他の事実（〈事実〉）から決め直せる値ですか」 | ライフサイクルを扱わず決め直せるなら、導出される値オブジェクトにする案を推奨する（例: 顧客の予約資格は、顧客の予約で起きた無断不利用から決まる値であり、顧客も資格も集約ではない） |
| 導出される値が識別子を持つか | 「〈値〉は〈誰の〉値かを自分で持ちますか（取り違えを生成で止めるため）。それとも呼び手が対応を保証しますか」 | 持たせる案を推奨する（受け取る側の生成の条件で「値の〈識別子〉と自分の〈識別子〉が同じ」を確かめられる） |
| 集約の操作が発さない業務イベント | 「〈業務イベント〉はどの集約のどの操作の事後条件として起きますか。どの操作も発さないなら、別の文脈の事実か導出結果の言い換えです」 | 集約の操作が発するものは判断を始めなくてもドメインイベントにし、発さないものは載せない案を推奨する |
| 集約どうしの協働の手段 | 「〈集約A〉と〈集約B〉は、識別子で参照／値として渡す／ドメインイベント／呼び手が両方を操作のどれで協働しますか。同じ操作で一貫させますか、結果整合ですか」 | 別の集約を保持しない前提で、同じ操作で一貫させる必要が無ければドメインイベントか呼び手の操作（結果整合）を推奨する |
| 正本の未決がモデルに及ぼす影響 | 「正本の未決〈…〉が決まるまで、〈要素〉に〈操作〉を置きませんが、よいですか」 | 置かない案を推奨する |

`context`には、`purpose`（この正本の業務概念を要素と操作の契約へ割り当てる）、`audience`（業務を形にするエンジニア）、`boundary`（業務知識の追加・反証、永続化、実装、層構成、画面、APIは扱わない）を渡す。

### ground

依頼、正本のpath、決定と未決を1つに束ねる。`--source`は必ず1本である。更新の依頼なら`--existing`に既存資料の絶対pathを渡す。

### index-source

正本から機械的に語を抜き出す。**ここで意味の判断をしない。** 索引に無い語は要素にできない、という検査の材料を作るだけである。正本が契約の節を持たなければ止まり、正本を直してもらう。

### assign

自分のpackageの`assign-domain-model`skillが担う。割り当ての判断は、そのskillの参考資料（対応規則・割り当ての規律・要素ごとの問い）にある。この段取りはそれを持たない。

### verify

述語だけを見る。通ったときに言えるのは「その述語が成り立った」ことだけで、「モデルが正しい」ではない。`warnings`は合否に影響しない索引であり、報告に写して人が読み返す。

**通らなかったときに検査を緩めない。** 候補を直す。候補が直せないのは、正本の側に問題があるときで、そのときは正本の反証へ戻す。

### assemble → document

素材は「正本のpath、決定、未決、索引の要約、検査済みモデル」の順で束ねる。`write-doc`には`document_type: domain-model`と、[成果物の形](deliverable.md)を`references`として渡す。型の実現方法、テンプレート、記載例はwrite-doc側に委ねる。

### cleanup

自分が作った中間成果物（束ねた入力、索引、候補、検査済み、素材）だけを消す。正本と最終資料は残す。
