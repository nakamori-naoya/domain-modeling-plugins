# ドメイン要素へ割り当てる判断規律

`assign`工程で同じagentが、正式な定義、索引、確認済み決定とともに適用する。

## 正式な定義からの写像

- 業務用語は、同一性で区別し状態が変わっても追うならエンティティ、値で区別し生成時から制約を守るなら値オブジェクト、複数概念を一つの不変条件で束ねる境界の根なら集約ルートの候補にする。
- 集約操作の事後条件として起きる業務イベントはドメインイベント候補にする。別文脈の事実や導出結果の言い換えは捨てた割り当てへ送る。イベントを事実の置き場にしない。
- 一要素の内側で守れる規則はその不変条件、複数要素にまたがる規則は集約の不変条件、どの集約でも守れない規則は守る場所を明示した集約間不変条件または未決にする。
- 状態で呼べる操作が異なるときだけ型を分ける。アクターは型にせず、操作の事前条件と拒む理由へ写す。
- 成立条件は事前条件、成立後の状態は事後条件、業務上の不成立理由は拒む理由へ写す。
- BDDごとに要素・操作・不変条件を対応させ、対応しない要素や操作は残さない。

## 割り当ての規律

1. 正式な定義の明示索引にない語を要素にしない。本文にだけ現れる語も要素には使わず、必要ならdomain-ruleの対応する索引対象節へ追加するため反証へ戻す。
2. 属性の形が同じでも、目的・場面・文脈が違えば別要素にする。
3. 並び順、合計、重複、先頭選択など集合の規則を一件の要素へ持たせない。正式な定義に集合要素がなければ呼び手の手順へ置く。
4. 「できるか確認」と変更を分けず、判断を事前条件、変更を事後条件、不成立を拒む理由にした一操作へまとめる。判定だけを使うBDDがある場合だけ独立判定を置く。
5. 値オブジェクトは不変にする。状態を持つ集約ルートには、どの不変条件を一操作で守るためかを書く。
6. BDDに対応しない要素・操作は詳細から外し、捨てた割り当てへ理由つきで移す。
7. 複数集約の協働には、識別子参照、値渡し、ドメインイベント、呼び手が両方を操作、のどれかと、渡すもの、一貫性、片側だけ成立した場合を明示する。
8. 列、レコード、テーブル、DB、永続化などデータ配置の語で業務事実を書かない。

## 各要素へ答える問い

- 目的: 何を一か所へ閉じ、何を成し遂げるためにあるか。
- 何でないか: 同じ属性を持つ隣接概念と、目的・場面のどこが違うか。
- 持つもの: 技術型でなく業務語で何を持つか。
- 不変条件: 生成後、どの操作を経ても何が成り立つか。その要素だけで守れるか。
- 生成の条件: 何が揃わなければ存在できないか。外で保証する条件は何か。
- 協働相手: 呼び手と参照要素は誰か。別集約ならどの手段で協働するか。
- 操作: 事前条件、事後条件、拒む理由、発するイベントは何か。どのBDDで使うか。
- 状態と型: 状態ごとにできる操作・できない操作は何か。公開操作集合が違うため型を分ける必要があるか。

答えがない欄は空欄にせず、`なし`または未決へ送る理由を書く。
