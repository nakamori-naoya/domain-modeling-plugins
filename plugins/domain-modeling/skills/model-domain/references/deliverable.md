# 成果物の形 — ドメインモデル資料

**成果物は、業務知識・コアドメインの正本を写したドメインモデル資料1本である。** 業務を形にするエンジニアが、実装の前に同じ要素・同じ境界・同じ操作の契約を思い浮かべるために作る。

## 読み手と用途

- 業務を形にするエンジニアは、何を要素にし、どこに集約の境界があり、どの状態で何ができるかを確認する
- レビューする人は、割り当ての理由と、捨てた案、未決を読み、モデルが正本のどこから来たかを辿る
- データモデルや実装の担当者は、この資料を入力にして、それぞれの資料で永続化や型設計を決める

この資料は、永続化、テーブル、言語固有の型、クラスの書き方、層構成、画面、APIを決めない。それらは「この資料に書かないもの」で検討先だけを示す。

## 構成

節は次の11個で、順序を変えない。

1. **目的と範囲** — 元にした正本、扱うコアの範囲、対象外にした概念とその理由
2. **要素一覧** — 要素名／種別／正本のどの語か／一文の目的
3. **モデル図** — 集約ごとに1枚の Mermaid classDiagram。各集約の直下に責務（一文）と境界（この内側で一貫させる不変条件）を書き、図にはルート・内側の要素・発するドメインイベント・参照する他の集約（外部の集約）を描く。メソッドは公開コマンド（状態を変える操作と生成）だけで、フィールドとゲッターは描かない。集約が2つ以上なら「集約どうしの関係」の図を1枚足す。合意するのは振る舞いと境界であって、データの持ち方ではない
4. **各要素の詳細** — 要素ごとに `###`、項目ごとに `####`（目的・何でないか・持つもの・不変条件・生成の条件・協働相手）、操作ごとに `#### 操作: <操作名>`（事前条件・事後条件・拒む理由・発するイベント）。表にしない
5. **集約の境界** — どの要素がどの集約の内側か、集約をまたぐ参照は識別子か値か、複数要素にまたがる不変条件をどこで守るか
6. **状態と型の分割** — 状態を持つ要素について、各状態で可能・不可能な操作と、型を分けたか分けなかったかの理由
7. **ドメインイベント** — 集約の操作が発するもの全部。発する要素・操作と、始める判断（この文脈で無ければそう書く）。イベントは通知であって事実の置き場ではない
8. **BDDとの対応** — 正本の各BDDがどの要素のどの操作と不変条件で成立するか。対応しないBDDと、対応のない要素・操作
9. **捨てた割り当て** — 候補にして採らなかった案と理由
10. **未決** — 正本の未決のうちモデルに影響するものと、モデル固有の未決。何が分かれば確定するか
11. **この資料に書かないもの** — 技術事項と、その検討先

## 各要素に必ず書く項目

| 項目 | 答える問い |
|---|---|
| 目的 | 何を成し遂げるためにあるか（1文） |
| 何でないか | 隣接する概念との境界。取り違えやすい語と、何が違うか |
| 持つもの | 業務語で書いた属性。型名ではなく概念 |
| 不変条件 | 生成後、どの操作を経ても常に成り立つこと |
| 生成の条件 | 何が揃えば存在できるか。揃わなければ存在しない |
| 協働相手 | 呼び手（判断権者）と、参照する要素 |
| 操作 | 操作ごとに、事前条件／事後条件／拒む理由／発するイベント |

「協働なし」「操作なし」「拒む理由なし」「発するイベントなし」も省略せず明記する。空欄は、調べた結果の不存在なのか見落としなのかを区別できない。

## 書き方の規律

- 要素の名前は正本のユビキタス言語の語をそのまま使う。言い換えない
- 事前条件・拒む理由は、正本の「業務ルール」「拒むときの理由」の語で書く
- 「確認する」と「変更する」を別の操作に分けない。判断は事前条件、変更は事後条件に書く
- 型名（`string`、`int`、クラス名）や、`getter`／`setter`／`repository`の語を使わない
- 未決が残る要素は、確定した要素と同じ書き方で見せない。未決の節に対応する行を置く
