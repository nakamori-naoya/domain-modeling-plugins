# 実行指示書 — model-domain

`playbook.yml`は工程順・依存・入出力を決める。この文書は、各工程で何を意識するかと、grillへ渡す題材固有の文脈を補う。

## 背景と目的

業務知識・コアドメイン（domain-rule）の正本は、業務として何が正しいかを確定させる。それだけでは、エンジニアが同じモデルを思い浮かべるには足りない。同じ正本を読んでも、何を要素にし、どこに境界を引き、どの操作をどの要素に置くかは人によって違う。

この段取りは、その違いを一つの資料へ収束させる。**成果物は共通理解の材料であって、実装コードではない。** 言語固有の型やクラスの書き方には踏み込まない。

## 前提

- 正本は業務知識・コアドメイン（domain-rule）型の資料で、`# 概要`から`# BDD`までの見出しを持つ
- 正本の未決は、この段取りで決めない。モデル側の未決として引き継ぐ
- 正本に無い業務の概念が要ると分かっても止まらない。その語を要素にせず、名前・なぜ要るか・導いた業務ルール・BDD・足すべき節を「正本へ提案する概念」に残して資料を完成させる。正本はこの段取りで書き換えず、提案は正本の反証（`formulate-domain`）へ渡す

## 工程ごとに意識すること

### index-source

`source.py`が正本から語を機械抽出し、標準出力へJSONで返す。**ここで意味の判断をしない。** 索引に無い語は要素にできない、という検査材料を作る。索引はfileに書かず、`verify.py`が同じ正本pathから同じ索引を導く。正本が契約の節を持たなければ止まり、正本を直してもらう。

### settle（grill）で確かめること

**正本と索引から読み取れることは問わない。** 業務用語の意味、業務ルールの成立条件、拒む理由は正本にある。問うのは、正本だけでは一つに決まらない割り当てである。

**問う数の上限と対話の作法は`grill`の公開契約に従う。** 下の論点は候補であり、全部を問う一覧ではない。候補のうち次の基準で選び、成果を左右する順に並べて渡す。選ばなかった論点と、上限で問われずに`open_questions`で返った論点は「推奨の作り方」の案を仮置きして`assign`へ渡し、`## 未決`に仮説として載せる。

- 選ぶ: 回答によって集約の境界、状態ごとの型の有無、要素の有無、協働の手段（同じ操作で一貫させるか結果整合か）が別物になる論点。正本の索引と「常に守られること」だけでは一つに決まらない論点。
- 選ばない: 推奨の作り方どおりに置いても要素一覧と操作の契約が変わらない論点。値オブジェクトの識別子の有無のように資料を見てから確かめれば足りる論点。正本の未決の影響のように「置かない」が既定で決まる論点。
- 2回目の`grill`は利用者が求めた場合か、決定なしでは本文を完成できない場合だけ行う。

| 論点 | 問い方 | 推奨の作り方（問わないときはこれを仮置きする） |
|---|---|---|
| 集約の境界 | 「〈常に守られること#n〉は〈概念A〉の内側だけで守れますか。〈概念B〉も同じ操作で一貫させますか」 | 1つの操作で一貫させたい範囲を最小にする案を推奨し、広げる案は理由を添えて対案にする |
| 状態ごとの型の分割 | 「〈状態を持つもの〉は、状態によって呼べる操作が違いますか。違うなら状態ごとに型を分けますか」 | 正本の「状態と、その移り変わり」で、状態ごとに引き金が違えば分ける案を推奨する |
| 正本に無い語 | 「〈語〉を要素にしたくなりますが、正本のユビキタス言語にありません。正本へ足す提案として残し、今回は要素にしなくてよいですか」 | 要素にせず「正本へ提案する概念」へ残す案を推奨する。この段取りは正本を書き換えず、提案を反証へ渡す |
| 形が同じ2つの語 | 「〈語A〉と〈語B〉は属性が同じに見えます。目的や場面が違えば別の要素にしますが、同じ概念ですか」 | 別の要素にする案を推奨する |
| 識別子を持つが集約か | 「〈概念〉は〈識別子〉ごとに決まりますが、この文脈で〈概念〉の生成から終端までを扱いますか。それとも他の事実（〈事実〉）から決め直せる値ですか」 | ライフサイクルを扱わず決め直せるなら、導出される値オブジェクトにする案を推奨する（例: 顧客の予約資格は、顧客の予約で起きた無断不利用から決まる値であり、顧客も資格も集約ではない） |
| 導出される値が識別子を持つか | 「〈値〉は〈誰の〉値かを自分で持ちますか（取り違えを生成で止めるため）。それとも呼び手が対応を保証しますか」 | 持たせる案を推奨する（受け取る側の生成の条件で「値の〈識別子〉と自分の〈識別子〉が同じ」を確かめられる） |
| 集約の操作が発さない業務イベント | 「〈業務イベント〉はどの集約のどの操作の事後条件として起きますか。どの操作も発さないなら、別の文脈の事実か導出結果の言い換えです」 | 集約の操作が発するものは判断を始めなくてもドメインイベントにし、発さないものは載せない案を推奨する |
| 集約どうしの協働の手段 | 「〈集約A〉と〈集約B〉は、識別子で参照／値として渡す／ドメインイベント／呼び手が両方を操作のどれで協働しますか。同じ操作で一貫させますか、結果整合ですか」 | 別の集約を保持しない前提で、同じ操作で一貫させる必要が無ければドメインイベントか呼び手の操作（結果整合）を推奨する |
| 正本の未決がモデルに及ぼす影響 | 「正本の未決〈…〉が決まるまで、〈要素〉に〈操作〉を置きませんが、よいですか」 | 置かない案を推奨する |

`context`には、`purpose`（この正本の業務概念を要素と操作の契約へ割り当てる）、`audience`（業務を形にするエンジニア）、`boundary`（業務知識の追加・反証、永続化、実装、層構成、画面、APIは扱わない）を渡す。`references`には正本の絶対pathと、入口の`references`入力をそのまま渡す。

### assign

同じagentが[ドメイン要素へ割り当てる判断規律](modeling-judgment.md)、[対応規則](mapping.md)、[割り当ての規律](disciplines.md)、[要素ごとの問い](element-questions.md)を全文読み、正本、索引、対話の決定と未決を一つの文脈で適用する。値オブジェクト、エンティティ、集約ルート、ドメインイベント、例外的なドメインサービスへの対応、8つの割り当て規律、各要素へ答える問いを満たす本文を作る。別skillや別agentへ意味判断を渡さない。

### verify

候補本文を標準入力で渡し、正本pathから導いた索引に対して述語だけを見る。通ったときに言えるのは「その述語が成り立った」ことだけで、「モデルが正しい」ではない。明示索引に無い語は本文中に現れていても失敗する。`warnings`はそれ以外の合否に影響しない箇所を報告へ写して人が読み返す。

**通らなかったときに検査を緩めない。** 候補を直す。索引に無い語が要るなら、その語を要素から外して「正本へ提案する概念」へ移す。提案した語は要素一覧に残さない。

### document

検査済み本文を`{kind: text, content: <完成本文>}`として直接渡す。`write-doc`には`document_type: domain-model`と、入力の`references`をそのまま`references`として渡す。新規なら`output_directory`と`name`、更新なら`existing_document_path`を`update_target`として排他的に渡す。型の実現方法、テンプレート、記載例はwrite-doc側に委ねる。値運搬だけの素材fileは作らない。保存後に消すべき一時fileは無い。
