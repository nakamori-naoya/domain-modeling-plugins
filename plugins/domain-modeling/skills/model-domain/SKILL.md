# model-domain（図で議論できるドメインモデルを作る）

domain-rule資料1本から、エンジニアが図を囲んで境界とコマンドを議論できるドメインモデル資料1本を作って保存する。この資料は議論に使うので、図が主役である。クラス図は、何が集約で、何を内側に持ち、何を識別子で指し、どのコマンドを受け付け、何を発するかを示す。状態遷移図は、どの状態でどのコマンドを受け付け、何になるかを示す。文章は図で表せないことにだけ使う。図の言い直しが増えるほど、議論したい境界とコマンドが埋もれるからである。

## 判断の要

割り当ての前に [references/modeling.md](references/modeling.md) を全文読む。判断の大半は次の五つで決まる。

**集約の境界は、一つのコマンドで一貫させたい不変条件が届く範囲に引き、それより広げない。** 上限、重複、順序のような集合への規則は一件の集約の中では確かめられない。それを守るために集約を広げず、呼び手がその時点の事実を値にして渡すか、集約の外の誰が守るかを書く。

**判定だけの操作を作らない。** 確認と変更を分けず、判断を事前条件、変更を結果、不成立を拒む理由にした一つのコマンドにする。状態によって受け付けるコマンドが違うなら状態遷移図に描き、矢印はコマンドだけにする。

**矢印の出ていない（状態、コマンド）の組には、拒む理由を書く。** その状態でそのコマンドを呼ばれたときの業務上の理由を、コマンドの節に状態ごとに一文で書く。業務知識にその理由が無ければ推測で補わず、提案に回す。

**語は domain-rule 資料からだけ取る。** 図のクラス、コマンド、状態には、domain-rule資料のユビキタス言語と状態遷移図の語だけを使う。無い語や決まり、無い状態が要ると分かったら、図に使わず「業務知識への提案」に書き、domain-rule資料の反証（bdd の `formulate-domain`）へ渡す。形が同じでも目的が違えば別の要素にし、識別子を持つだけのものは集約にしない。

**文章は図の言い直しをしない。** 一つの論点は一か所にだけ書く。業務の決まりが薄い概念には節を置かず、クラス図に描くだけにする。

分からないことに出会ったら、それが集約の数と境界、要素の種別、集約の外の守り手、状態ごとに受け付けるコマンドのどれかを変えるかで決める。変えるなら推測で埋めずに止まり、何が分からないか、結論のどこが変わるか、推奨する答えを返す。変えないなら最も筋の良い案を仮説として置き、該当箇所で仮説だと分かるように書いて、`## 未決` に根拠と採らなかった案を残す。

## 入力

domain-rule資料の絶対パスを1本受け取る。無い、または複数なら、どれから作るかを尋ねて止まる。新しく作るなら保存先のディレクトリと `.md` の名前を、更新するなら同じdomain-rule資料から作った既存のドメインモデル資料の絶対パスを受け取る。新しい保存先が依頼に無ければ、一度だけ提案して確認を待つ。同じ名前のファイルがあれば止まる。追加で従う資料があれば、絶対パスで受け取って最初に読む。

## 進め方

1. domain-rule資料と依頼を読み、答えによって図の形（集約の数と境界、集合への規則の守り手、要素の有無）が変わる割り当てだけを grill で確かめる。domain-rule資料から読み取れることは問わない。
2. write-doc skill の `assets/templates/domain-model.md`（どの節に何を置くかと、検査が読む目印）と `references/writing-norms.md`（書くときの規範）を読み、図を先に描いてから、図で表せないことだけを書く。更新では、domain-rule資料の変更と依頼が及ぶ箇所だけを書き換える。
3. 資料を保存し、`python3 scripts/verify.py --source <domain-rule資料の絶対パス> < <保存した資料>` を一回かける（パスはこの SKILL.md のディレクトリ基準）。検査は、図の語がdomain-rule資料にあること、種別とコマンドの置き場、状態遷移図の状態と矢印、矢印の無い組がある集約に拒む理由の節があること、引いたBDD番号を見る。見出しの文言は読まない。通らなければ資料を直す。検査を通すためにdomain-rule資料の語を言い換えず、索引に無い語は図から外して提案へ移す。

## 報告

保存した資料と元にしたdomain-rule資料の絶対パス、集約の境界とその理由、未決と何が分かれば確定するかを返す。業務知識への提案があれば、次の一手として、保存した資料を `references` に渡して `formulate-domain`（bdd）でdomain-rule資料を反証・更新することを示す。検査の `warnings`（本文が引いていないBDD）は、集約の外で成り立つものか要素の不足かを読み返して報告する。
