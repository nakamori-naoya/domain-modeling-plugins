# model-domain（図で議論できるドメインモデルを作る）

読み終えると、domain-ruleの正式な定義1本から、エンジニアが図を囲んで境界とコマンドを議論できるドメインモデル資料1本を保存できる。

この資料は議論に使う。だから図が主役である。クラス図は、何が集約で、何を内側に持ち、何を識別子で指し、どのコマンドを受け付け、何を発するかを一目で示す。状態遷移図は、どの状態でどのコマンドを受け付け、何になるかを示す。文章は、図だけでは表せない三つに絞る。境界をそこに引いた理由と、その内側で守ること。コマンドが何を受け取り、どの条件で成立し、何を拒むか。取り違えやすい語が何でないか。すべての要素に同じ項目を埋める書き方はしない。要素を並べた説明が増えるほど、議論したい境界とコマンドが埋もれるからである。

割り当ては写像であって、発見ではない。図に使う語は正式な定義のユビキタス言語だけである。正式な定義に無い語や決まりが要ると分かっても止まらず、図には使わずに「業務知識への提案」へ書いて資料を完成させる。この入口が書き換えてよいのは、自分が保存するドメインモデル資料だけである。正式な定義は書き換えず、提案は報告で`formulate-domain`（bdd）へ渡す次の一手として示す。

同じdirectoryの`playbook.yml`が工程順の定義である。このSKILLを読んだagentが、正式な定義、依頼、対話結果を保持したまま`steps`を宣言順に辿る。候補本文はインメモリで保持し、作業directoryや一時fileは作らない。

## 入力

`domain_rule_path`は必須で、domain-ruleの正式な定義の絶対path 1本である。無ければ「どのdomain-rule資料を正式な定義にしますか（絶対path）」、複数なら「どれを正式な定義にしますか。モデルは正式な定義1本につき1本です」と返して止まる。指されたfileが`# 概要`から`# BDD`までの見出しを持たなければ、domain-rule型ではないと返して止まる。

`user_input`は依頼文で、新規か更新か、既知の割り当て方針を含む。`references`は任意で、追加で従う資料の絶対path配列である。手順の最初に読む。相対path、読めないpath、symlinkは契約に反する入力として止まる。

保存先は、更新なら`existing_document_path`（同じ正式な定義から作った既存資料の絶対path）、新規なら`output_directory`（書き込める既存の絶対directory）と`name`（path要素を含まない`.md`file名）で受け取り、両者は排他である。新規の保存先が依頼に無ければ、既存資料の構成を読んで置き場と名前を一度だけ提案し、確認を待つ。同名fileがあれば止まる。依頼に無い既存資料を探して更新扱いにしない。

## 判断の本質

割り当ての前に[割り当ての判断](references/modeling.md)を全文読む。判断の大半は次の四つで決まる。

**集約の境界は、一つのコマンドで一貫させたい不変条件が届く範囲に引き、それより広げない。** 集合への規則（上限、重複、順序）は一件の集約の中では確かめられない。それを守るために集約を広げず、呼び手がその時点の事実を値にして渡すか、集約の外の誰が守るかを書く。

**状態によって受け付けるコマンドが違うなら、状態遷移図に描く。** 図の矢印はコマンドだけで、判定だけの操作は描かない。確認と変更を分けず、判断を事前条件、変更を結果、不成立を拒む理由にした一つのコマンドにする。

**語は正式な定義から取り、形が同じでも目的が違えば別の要素にする。** 識別子を持つだけでは集約にならない。この文脈でその生成から終端までを扱うものだけを集約にし、ほかの文脈のものは識別子の値オブジェクトとして指す。複数の文脈で使う値には「文脈共有」の印を付ける。

**文章は図の言い直しをしない。** 図から読めることを書き足したくなったら、その文を消す。残すのは、境界の理由、不変条件と集約の外の守り手、コマンドの契約と拒む理由、何でないか、だけである。

成果物の型（図の記法、節の置き方）はwrite-docの`domain-model`型のtemplateが定める。この入口は本文を作って`document_type: domain-model`で保存する。

## 手順

1. **index-source（`scripts/source.py`）。** `python3 scripts/source.py --playbook playbook.yml --source <domain_rule_path>`を実行する（pathはこのSKILLのdirectory基準）。正式な定義から業務用語、業務イベント、コマンド、概念、状態、BDD番号を抜き出し、終了code 0で標準出力へ索引JSONを返す。`vocabulary`が図のクラスに使える語、`commands`がコマンドに使える語、`states`が状態遷移図に使える状態である。業務用語、コマンドとクエリ、BDDの節が無いか空なら終了code 2と診断を標準エラーへ返すので、正式な定義を直してもらうよう報告して止まる。

2. **settle（`grill`）。** 正式な定義と索引から読み取れることは問わない。問うのは、答えによって図の形（集約の数と境界、集合への規則の守り手、状態の分け方、要素の有無）が変わる割り当てだけで、成果を左右する順に推奨を添えて渡す。入力は`contract: grill/grill`、`version: 1`、`topic`（題材名）、`context`（`purpose`: 業務概念をドメインモデルの図へ割り当てる、`audience`: 業務を形にするエンジニア、`boundary`: 業務知識の追加・反証、永続化、実装、層構成、画面、APIは扱わない）、`questions`（`{id, question, recommendation}`）、`references`（正式な定義の絶対pathと入力の`references`）である。問う数と対話の作法は`grill`の公開契約に従う。返った結果の`status`が`completed`で、`decisions`と`open_questions`が配列であることを確かめ、欠落や別の型なら止まる。`open_questions`は推奨を仮置きして次へ渡す。

3. **assign。** 図を先に描く。クラス図に全要素と関係とコマンドを描き、状態を持つ集約ごとに状態遷移図を描く。次に、図で表せないことだけを文章にする。集約ごとの節に境界の理由と守ることを書き、クラス図のコマンドごとに、受け取るもの、成立する状態と条件、結果と発するイベント、拒む理由（正式な定義の「拒むときの理由」の語を「」で）、成立するBDDの番号を書く。取り違えが起きる語があるときだけ、何でないかを書く。仮置きした割り当ては該当箇所で仮説と分かるように書き、`## 未決`に論点、仮置き、根拠、採らなかった案を残す。正式な定義に無い語や決まりが要るなら`## 業務知識への提案`に書く。

4. **verify（`scripts/verify.py`）。** 候補本文を標準入力で`python3 scripts/verify.py --playbook playbook.yml --source <domain_rule_path>`へ渡す。scriptは手順1と同じ索引を正式な定義から導き、図の語が索引にあること、種別とコマンドの置き場、状態遷移図の状態と矢印、コマンドごとの節、引いたBDD番号、提案の語と図の非重複を検査する。終了code 0なら標準出力に`verified`、`source_path`、`warnings`を返す。終了code 2なら診断（標準エラー）に従って`assign`へ戻り、候補を直す。検査を通すために正式な定義の語を言い換えない。索引に無い語が要るなら、図から外して提案へ移す。渡し方の例:

   ```bash
   python3 scripts/verify.py --playbook playbook.yml --source /absolute/path/to/domain-rule.md <<'MD'
   # <題材>のドメインモデル
   ...
   MD
   ```

5. **document（`write-doc`）。** 検査済み本文を`{kind: text, content: <完成本文>}`の1要素配列で`material`に、`domain-model`を`document_type`に、入力の`references`を`references`に渡す。新規なら`output_directory`と`name`、更新なら`existing_document_path`を`update_target`として排他的に渡す。返った`status`が`completed`で、`path`が指定した保存先と一致することを確かめる。`failed`、結果の欠落、pathの不一致なら理由を報告して止まる。

## 更新するとき

更新で書き換えるのは、正式な定義の変更と依頼が及ぶ箇所だけである。既存の資料が、今回の変更と関係ない箇所で現在のtemplateや検査に合わないことがある。その箇所は書き換えず、何が合わないかと、直すなら何をどう変えるかを報告に返す。今回の変更の結果として検査に通らないときだけ、候補を直す。

## 停止条件

次の場合は止まり、部分的な候補を保存して完了にせず、どこまで確定し、何が分かれば続けられるかを返す。正式な定義のpathが無い、複数ある、domain-rule型でない。`source.py`が終了code 2で終わった。`grill`が`completed`以外を返したか、結果の型が違う。新規の保存先が決まらない、または同名fileがある。候補を直しても`verify.py`が通らない。`write-doc`が`completed`以外を返した。推奨の無い未決のうち、判断者の決定が要り仮説を置けないものがある。

次の場合は止まらず、仮説を明示して進む。正式な定義からも決定からも決まらない割り当ては、最も筋の良い案を仮置きして`## 未決`に残す。正式な定義に無い語や決まりが要るときは、提案に書いて資料を完成させる。

## 報告

保存した資料の絶対pathと、元にした正式な定義の絶対pathを返す。集約の境界とその理由、状態とコマンドの対応を短く書く。業務知識への提案が1件でもあれば、次の一手として「`formulate-domain`（bdd）へ、保存したドメインモデル資料の絶対pathを`references`として渡し、正式な定義を反証・更新する」を示す。未決と、何が分かれば確定するかを書く。検査の`warnings`（本文が引いていないBDD）は、集約の外で成立するものか要素の不足かを読み返す箇所として写す。検査が通ったときに言えるのは、判定した構造の述語が成り立ったことだけで、モデルが正しいことではない。
