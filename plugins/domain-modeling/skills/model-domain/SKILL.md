# model-domain

業務知識のBDDは、業務上何が成立し、何を拒み、どんな結果になるかを決める。しかし、その判断をどの単位が持ち、どの事実を外から受け、一回の変更で何を守るかには複数の設計がありうる。この差を埋める**議論の叩き台**を作る。モデルは実装の型や関数の確定図ではない。図と短い文章で、採る案、そうする理由、残る別案と未決を見えるようにする。

## 何を設計するか

最初に、業務知識からそのまま実装できる判断と、割り当てによって結果や安全性が変わる判断を分ける。後者だけをモデルの中心に置く。詳しい判断の観点は [references/modeling.md](references/modeling.md) を読む。

**一回で守る境界。** 成立した結果が同時に揃わなければならない範囲を示し、集約の内側で守れる決まりと、複数件・別文脈にまたがる保証を分ける。外の事実を使うなら、どの判断に必要で、いつの事実でなければならないかを示す。取得手段やトランザクション方式は決めない。

**同じものの生涯と判断の持ち主。** 業務上、何を同じ一件として追い、どの変化で扱いが変わるかを示す。状態によって受ける行いが変わるなら、初めの姿だけでなく、遷移後も判断を続ける姿にその判断を割り当てる。分け方は [references/modeling.md](references/modeling.md) に従う。状態図は境界や責務を議論するのに必要な節目だけを描く。コマンドやイベントは、それをどこに置くかで設計が変わるものを示し、全BDDの操作・拒否・引数を図へ写さない。業務知識に無い保存可能な業務状態は作らない。完全な値を組み立てるための未保存の下書きは、業務上の状態と区別し、実装側で選べる形として扱う。

**値と読み取りの判断。** 業務の条件を値だけで守れるところは値を中心に置き、同一性と生涯に伴う判断だけを集約に残す。値の区別や計算結果が規則を守る単位を変えるなら、その関係を示す。特に値の範囲、単位、必須の組、許容する種類、境界日の包含によってBDDの成立・拒否が変わるなら、判断の持ち主とその条件を文章で示す。図に属性や定数を網羅するためではなく、値の条件を別の一件の合計や後続の状態へ誤って移さないためである。読み取りで候補選択・順位・計算が業務の中心なら、その判断に要る値、結果、担い手を示す。誰が結果を読めるかも業務が決めるなら、その判断の境界を落とさない。取得して表示するだけなら、この業務のモデルを無理に作らない。すべての名詞を値オブジェクトにせず、読み取りのために集約を作らない。

## 叩き台の粒度

図は議論したい関係だけを描き、文章は図では分からない理由と未決に使う。採用候補の概念名は、業務知識の語で表せればそれを使う。業務知識に無い設計上の仮名が必要なら仮説と明示して置き、業務上の新しい語や決まりが必要なら持ち主への提案にする。候補を正本の語に見せない。クラスの全属性、全操作のシグネチャ、値の全種類、全状態の組合せ、拒否理由の網羅、コンストラクタ、版、テーブル、API、層構成は定義しない。後続の資料と実装が必要な細部を決める。

分からないことは、境界、判断の持ち主、値の意味、読み取りの結果を変えるかで扱う。変えるなら `grill` で確かめ、決まらなければ一案を確定させず、候補と影響を未決として示す。変えない細部は筋のよい仮説を明示して進む。一部が未決でも、独立して決まる関係は描く。中心の境界を描けないほど材料が無ければ、図を装わず欠落と確かめる相手を返す。

## 入力と進め方

業務知識の資料を一つ受け取り、その文脈の業務の行い、状態、値、クエリ、BDDを読む。対象の判断が無ければ資料を作らず理由を返す。保存先は依頼の絶対パスを使い、指定が無ければ対象の資料を置く場所を一度だけ確かめる。既存の業務知識は書き換えない。

1. BDDを結果の根拠として読み、結果からは一意に決まらない責務と境界の論点を絞る。答えでモデルの中心が変わる問いだけ `grill` に渡す。
2. `write-doc` の domain-model 型の template と writing-norms を読み、議論に必要な図と理由を保存する。中心の境界には、別案を採ると保証や判断の置き場がどう変わるかを添える。別案でも業務結果を守れると提案するなら、その保証を引き受ける判断の持ち主を示す。守れない別案は反例と明示し、成立する代案と取り違えない。問いに答えが無ければ、仮説と代案の差を示す。
3. 保存した資料に `python3 scripts/verify.py --source <業務知識の資料の絶対パス> < <保存した資料の絶対パス>` を一回かけ、構文と参照の違反だけを直す。検査の成功を設計の正しさとみなさない。
4. 最後に業務知識の成立・拒否・読み取りの規則から、設計の見落としを探す。状態が移るなら、そこで起きる事実と、繰り返す行いで新たな事実が生じるかを照合する。外から受ける事実がどの判断に効くか、複数の条件から作る結果に重複や矛盾がないかを確認する。図の各要素を今の議論に要る理由へ戻し、要らない要素と仮の詳細を外す。未決を確定したふりで埋めない。

## 報告

保存した資料と入力の絶対パス、中心の割り当てと理由、議論が残る案、業務知識の持ち主へ返す提案を短く示す。最後に実際に照合した業務規則と、図から外した不要な候補または不要物が無いと判断した根拠も短く記す。検査で分かるのは構造だけであり、境界と責務の意味は本文を読んで評価した結果として報告する。
